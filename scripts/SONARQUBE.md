# Backend reports for SonarQube

Reporting is configured directly in the root `package.json` using the existing `node:test` runner, [`c8`](https://github.com/bcoe/c8) for coverage, and [`node-reporter-sonarqube`](https://github.com/sjinks/node-reporter-sonarqube) for test execution XML. No custom JavaScript runner, reporter, or TypeScript loader is required.

## First-time setup

Use Node.js 22.8 or newer. From the repository root, install the declared development dependencies and synchronize the lockfile:

```sh
npm install --include=dev
```

The configuration uses `c8` 11.x and `node-reporter-sonarqube` 1.x. Commit the resulting `package-lock.json` update before using `npm ci` in CI or Docker builds. The install was not executed in this session, so the lockfile still needs this update.

## Generate reports

From the repository root:

```sh
npm run test
```

This runs `tests/*.test.js` sequentially, displays test results and coverage in the terminal, and creates:

| File | Contents |
| --- | --- |
| `coverage/lcov.info` | Backend source coverage generated by `c8` |
| `test-report.xml` | Test execution results in SonarQube's generic format |

The `c8` section in `package.json` enables `all` and includes only `app.js`, `server.js`, and JavaScript under `controllers`, `middleware`, `services`, `modals`, `routes`, and `utils`. Backend files never loaded by tests appear as uncovered. Frontend, tests, scripts, and third-party code are outside this coverage scope.

The tools generate reports for completed test runs and retain a nonzero exit code when tests fail. Generated reports and `.scannerwork/` are ignored by Git. Scan reports from a completed run; an interrupted run or a startup failure may leave incomplete, missing, or stale reports.

For the optional existing goal of 100% backend line, branch, and function coverage, use:

```sh
npm run test:coverage
```

This runs the same report-generating test command, then checks the coverage thresholds. It does not run tests twice or wrap `c8` around itself. A configured threshold is not a claim of measured coverage.

## Import with your scanner

The root `sonar-project.properties` sets:

```properties
sonar.projectKey=inventory-sales-management-backend
sonar.sources=app.js,server.js,controllers,middleware,services,modals,routes,utils
sonar.tests=tests
sonar.test.inclusions=tests/**/*.test.js
sonar.javascript.lcov.reportPaths=coverage/lcov.info
sonar.testExecutionReportPaths=test-report.xml
```

Set `sonar.projectKey` to your existing SonarQube project's key, or override it when invoking the scanner. Configure `SONAR_HOST_URL` and `SONAR_TOKEN` in your environment or CI settings. The scanner must already be installed/configured; running tests generates local reports and does not upload results.

Run from the repository root after the reports are generated:

```sh
sonar-scanner
```

To use another project key without editing the file:

```sh
sonar-scanner -Dsonar.projectKey=your-backend-project-key
```

This setup analyzes backend source only. Frontend coverage requires its own test reports and analysis configuration. Test-report file paths are relative to the repository root. Generate coverage and run the scanner in the same checkout, especially when LCOV contains absolute file paths.

SonarQube imports [JavaScript coverage from LCOV](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/test-coverage/javascript-typescript-test-coverage) and [test outcomes from its generic execution XML format](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/test-coverage/generic-test-data). Generic execution XML is a separate format from JUnit XML. SonarQube Server displays [execution reports for branch analyses, including the main branch](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/test-coverage/test-execution-parameters#branches-only); pull-request analyses support coverage but do not display execution reports.

## CI order

After the first-time install and lockfile update have been committed:

1. Check out the repository and install backend dependencies with `npm ci --include=dev`.
2. Run `npm run test` or `npm run test:coverage`.
3. Run the SonarQube scanner with the configured host, token, and project key.

If these steps use different jobs or containers, transfer both `coverage/` and the root `test-report.xml` to the scanner job and keep source paths consistent. To import failed-test results, configure the scanner step to run after completed failing tests while retaining the test step's failure status. Do not replace the failed test exit code with a successful scanner exit code.
